# Guides

Guide pages are reader-goal paths through the evidence library. They do not create new evidence categories; they sequence existing `[paper]`, `[provider-doc]`, `[tested]`, `[vetted-tool]`, and `[sourced]` entries so a reader can make a scoped decision without browsing the whole taxonomy.

## Start With A Goal

- **[Get better LLM outputs](better-llm-outputs.md)** — choose prompting and architecture patterns only when they are worth the added cost or workflow complexity.
- **[Build an agent with testable boundaries](build-an-agent.md)** — separate agent loops, tool use, evals, and safety boundaries before shipping autonomous behavior.
- **[Choose a model or provider](choose-a-model.md)** — compare provider surfaces without treating model catalogs as timeless rankings.
- **[Add AI to an existing workflow](ai-in-existing-workflows.md)** — wire AI into shell, CI/CD, automations, or no-code flows without hiding the operational boundary.
- **[Think about local AI](local-ai.md)** — reason about local runners, workflows, and hardware using sourced or tested claims only.
- **[Read the foundations first](foundations.md)** — read the papers, architecture explainers, and safety entries in a useful order.

## How To Use These

Start with the guide that matches the decision in front of you, then follow its evidence links into `prompting/`, `agents/`, `providers/`, `learning/`, `extensions/`, `integrations/`, `self-hosted/`, or `tools/`.

The guide prose is deliberately narrow. If a claim is not backed by an existing entry, it should not appear here.
